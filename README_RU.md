# Реализация режима полета БВС по данным оптического потока

Проект содержит три уровня реализации.

Первый уровень — исследовательский Python-контур:

1. генерация реалистичного синтетического лога БВС;
2. преобразование данных оптического потока, дальномера и IMU в оценку горизонтальной скорости;
3. EKF для оценки относительного положения и скорости без ГНСС;
4. контроль качества канала ОП и формирование защитных статусов;
5. пример MAVLink-моста для чтения/передачи данных.

Второй уровень — профессиональное RTOS-ориентированное C++17-ядро:

1. детерминированная обработка `OPTICAL_FLOW_RAD` без зависимости от Python/Linux;
2. учет ориентации датчика относительно корпуса;
3. учет рычага установки датчика относительно центра масс;
4. safety state machine для `FLOW_NAV`, `DEGRADED_HOLD`, `FAILSAFE_LAND`;
5. innovation gate для EKF;
6. CMake-сборка и автономные C++-тесты.

Третий уровень — PX4 uORB/NuttX-модуль:

1. запуск C++ RTOS-ядра внутри PX4 flight stack;
2. подписка на `sensor_optical_flow`, `distance_sensor`, `vehicle_imu`, `vehicle_attitude`;
3. публикация диагностики через `debug_vect`;
4. интерфейс внешней одометрии подготовлен, но слияние скорости с EKF2 заблокировано до получения достоверной скорости по трем осям;
5. штатные команды `ofnav start`, `ofnav status`, `ofnav stop` в PX4 shell;
6. модуль не командует моторами; флаг `-e` отвергается, пока нет достоверного трехкомпонентного измерения скорости.

## Быстрый запуск Python-уровня

```bash
cd uav_oflow_navigation
python -m venv .venv
source .venv/bin/activate       # Linux/macOS
# .venv\Scripts\activate        # Windows

pip install -e .[dev]

python src/synthetic_data.py --out data/synthetic_oflow_log.csv --duration 90 --seed 42
python src/run_offline_demo.py --input data/synthetic_oflow_log.csv --outdir outputs
pytest -q
```

После запуска будут созданы:

- `data/synthetic_oflow_log.csv` — синтетический лог;
- `outputs/estimated_nav.csv` — результат оценивания;
- `outputs/trajectory_xy.png` — сравнение истинной и оцененной траектории;
- `outputs/velocity.png` — сравнение истинной и оцененной скорости;
- `outputs/status_summary.json` — сводка по статусам режима.

## Исследовательский модуль оценки движения по изображению

Для постепенного перехода от ОП-датчика к визуальной одометрии добавлен
`src/ground_visual_motion.py`. Модуль выполняет сопровождение характерных
точек (Лукас–Канаде), проверку прямого/обратного перемещения, оценку
геометрии по RANSAC и пересчет смещения изображения в относительную скорость
по **известной высоте** и калибровке камеры.

```bash
python -m pip install -e '.[dev,vision]'
python -m pytest -q tests/test_ground_visual_motion.py
```

Метод предназначен **только для офлайн-исследований** на нижней камере
при малых наклонах и приближении плоской поверхности. Он не является
VO/VIO, не устраняет накопленный дрейф и не включен в управление БВС.
Подробности и требования к исходным данным НИИВК:
`docs/CAMERA_MOTION_RU.md`.

## Непрерывная относительная визуальная одометрия (офлайн)

В `src/continuous_visual_odometry.py` реализована обработка **последовательности**
кадров нижней камеры, расчет относительной горизонтальной скорости и
перемещения по непрерывным наблюдаемым участкам. Пропуски кадров, резкие
изменения высоты и ориентации, потеря текстуры вызывают новый `segment_id`.
**Координаты различных участков не сшиваются** без внешней привязки.

При наличии пространственной калибровки `body_from_camera` (переход из
СК камеры в связанную СК БВС) новый модуль
`src/camera_rotation_compensation.py` компенсирует вращение камеры
между кадрами через калиброванную гомографию. Без этой калибровки
обнаруженное изменение крена/тангажа по-прежнему приводит к отказу
от оценки интервала.

**Это не VIO:** готовые значения ориентации используются для компенсации,
но совместное оценивание состояния камеры и ИИМ пока не реализовано.

Для воспроизводимой проверки на материалах НИИВК добавлен запуск:

```bash
python -m pip install -e '.[dev,vision]'
python -m src.run_camera_odometry --manifest data/frames.csv \
    --calibration data/camera.yaml --output-dir outputs/camera_vo
```

Состав `frames.csv`, калибровки и ограничения математической модели:
`docs/CONTINUOUS_CAMERA_ODOMETRY_RU.md`. Система остается исследовательским
офлайн-прототипом: полноценная VO/VIO и привязка по ортофотоплану требуют
последующей разработки и проверки на реальных данных.

## Временное согласование видеокадров и учет установки камеры

Офлайн-алгоритм может использовать отдельный журнал **бортовой оценки
ориентации по ИНС/автопилоту**, а не только углы из CSV кадров.
Кватернионы `qw,qx,qy,qz` интерполируются к середине экспозиции без
экстраполяции; допустимый временной разрыв и поправка временных шкал
настраиваются явно.

При известном `camera_offset_body_m` и проверенной матрице
`body_from_camera` учитывается перемещение камеры из-за поворота
БВС вокруг центра масс. При отсутствии синхронизации соответствующий
участок траектории прекращается, вместо продолжения недостоверных координат.

Дополнительно можно задать `velocity_error_assumptions` для
**расчетной** ковариации горизонтальной скорости. Это гипотетическая
модель по заданным погрешностям, а не экспериментально подтвержденная
ковариация для фильтра PX4.

```bash
python -m src.run_camera_odometry \
  --manifest data/frames.csv \
  --calibration data/camera.yaml \
  --attitude-log data/attitude.csv \
  --camera-to-attitude-offset-us 5000 \
  --max-attitude-gap-us 25000 \
  --output-dir outputs/camera_sync
```

Полная методика, системы координат и необходимые исходные данные НИИВК:
`docs/SYNCHRONIZED_VISUAL_INERTIAL_INPUTS_RU.md`.
Бортовой канал PX4 остается диагностическим; полноценная VIO и привязка
по ортофотоплану еще не реализованы.

## Сырые измерения ИИМ и исследовательское визуально-инерциальное слияние

`src/imu_preintegration.py` интегрирует угловые скорости и удельную силу
от ИИМ в системе NED, учитывает заданные смещения нуля датчиков и
прерывает оценивание при потере непрерывности измерений.
`src/horizontal_visual_inertial_filter.py` реализует горизонтальный РФК
для относительного положения, скорости и двух поправок смещения
акселерометров; визуальная скорость принимается по нормированной
инновации и с обязательной ковариацией.

`src/run_imu_visual_fusion.py` обрабатывает CSV журнал ИИМ вместе с
файлом `visual_odometry.csv`, полученным предыдущим этапом.
Модель пока **не содержит неопределенности пространственной
ориентации и онлайн-оценивания смещений гироскопов**; результат
не является готовой VIO и не передается в PX4.

Точный формат журналов, схема калибровки, уравнения и приемочные
ограничения — `docs/RAW_IMU_VISUAL_FUSION_RU.md`.

## Пятнадцатимерный фильтр ошибок состояния (исследовательская версия)

Новый модуль `src/error_state_inertial_filter.py` реализует
15-мерный фильтр ошибок с номинальными положением, скоростью,
ориентацией (кватернион) и смещениями нуля гироскопов/акселерометров.
Используется полная матрица ошибок 15×15, пересчет ковариации на
отсчетах ИИМ и коррекция по двум компонентам визуальной скорости
с проверкой нормированной инновации.

`src/run_eskf_offline.py` воспроизводит оценку по журналам ИИМ и
визуальной одометрии НИИВК; выход — относительная траектория и
отчет о принятых/отклоненных измерениях.

```bash
python -m src.run_eskf_offline \
  --imu-log data/imu.csv \
  --visual-log outputs/camera_sync/visual_odometry.csv \
  --config data/eskf_noise.yaml \
  --output-dir outputs/eskf
```

Точная математическая постановка, требования к исходной калибровке
и ограничения — `docs/ESKF_15_STATE_RU.md`. **Наличие 15 состояний
не доказывает их полную наблюдаемость**; на зависании курс, смещение
гироскопа по вертикальной оси и абсолютные координаты могут
оставаться ненаблюдаемыми. Программная модель не включается в PX4.

## Картографическая привязка по геопривязанному ортофотоплану

Добавлены `src/orthophoto_localization.py` и
`src/run_orthophoto_localization.py` — **офлайн-локализация** БВС по
изображению нижней камеры относительно метрически геопривязанного
ортофотоплана. Алгоритм проверяет соответствия ORB/RANSAC,
калибровку масштаба и ориентации, наклон оптической оси,
плечо камеры, распределение характерных точек и неоднозначные
привязки между листами карты.

`src/map_correction_gate.py` формирует только **кандидат на
последующую коррекцию**: без независимой калибровки ковариации
карты и учета корреляции с визуальной одометрией измерение
не может корректно объединяться с РФК. Изменения в
позиционном состоянии РФК и интерфейсе PX4 **не выполняются**.

```bash
python -m src.run_orthophoto_localization \
  --manifest data/camera_frames.csv \
  --configuration data/map_config.yaml \
  --output-dir outputs/map_localization
```

Дополнительно `src/map_temporal_integrity.py` проверяет
согласованность координат на последовательности кадров с
фиксируемым отказом при скачке положения и пропуске времени.
Сопоставление выполняется с несколькими гипотезами
**внутри одного листа** ортофотоплана, а не только между листами.

`src/run_map_reference_audit.py` сравнивает полученные
координаты с независимым эталоном по полетам, выделяет
геометрически принятые, но ошибочные привязки и их долю
для заданного порога ошибки в метрах.

Математическая постановка, структура геопривязки в метрах N/E,
форматы CSV/YAML и программа проверки НИИВК:
`docs/ORTHOPHOTO_LOCALIZATION_RU.md`.
Экспертная рецензия, устраненные дефекты и остаточные
ограничения — `docs/PR12_SCIENTIFIC_REVIEW_RU.md`.
Успешная синтетическая проверка при высоте 100 м не доказывает
готовность к длительному зависанию БВС без ГНСС.

## Сквозной стенд синтетических изображений камеры, ИИМ и дальномера

`src/synthetic_sensor_bench.py` создает физически согласованные
в пределах **модели плоской сцены** PNG-кадры нижней камеры,
измерения угловой скорости и удельной силы ИИМ (FRD),
высоту над плоскостью, временные метки экспозиции и задержки
доставки результатов камеры. Сцена и измерения рассчитываются

оценок и сравнивается с ними на корректных временных метках.
Доступны сценарии `nominal`, `yaw_rotation`,
`camera_blackout`, `imu_gap`, `duplicate_map`.

```bash
python -m src.synthetic_sensor_bench \
  --output-dir outputs/synthetic_sensor_bench \
  --scenario nominal --frames 6 --seed 72118
```

В CI публикуется артефакт `synthetic-camera-imu-integration`
с изображениями, CSV измерений и JSON/CSV результатами.
Точный протокол, модель луча и допущения —
`docs/SYNTHETIC_CAMERA_IMU_BENCH_RU.md`.

**Этот стенд не PX4 SITL и не подтверждение точности зависания
реального БВС на высоте 100 м.** Картографическая поправка
в ESKF/PX4 не вносится, управление отсутствует, архивов
НИИВК для его работы не требуется.

## PX4 SITL: безопасный диагностический replay синтетических датчиков

В POSIX/SITL-сборке модуля `ofnav` появилась отдельная
команда `sitl-replay`. Она читает синтетические
записи горизонтальной визуальной скорости и ИИМ,
согласованные по времени экспозиции и приведенные
к формату интегрального оптического потока C++-ядра.

**Данные не публикуются в uORB и не передаются
в EKF2 или исполнительные органы БВС.**
Для высоты 100 м C++-ядро по-прежнему должно
возвращать отказ `HEIGHT_TOO_HIGH`, поскольку
его прежний подтвержденный программный диапазон
составляет только 0,2–4 м. Это не готовая
навигация на 100 м.

```bash
python -m src.export_px4_sitl_replay \
  --results-csv outputs/synthetic_sensor_bench/evaluation/sensor_bench_results.csv \
  --camera-csv outputs/synthetic_sensor_bench/sensors/camera.csv \
  --imu-csv outputs/synthetic_sensor_bench/sensors/imu.csv \
  --output-csv outputs/ofnav_sitl_replay.csv

bash tools/run_px4_sitl_replay_smoke.sh \
  PX4-Autopilot outputs/ofnav_sitl_replay.csv outputs/px4_sitl_logs
```

Сборка PX4 v1.16.2 и проверка внутри исполняемого
PX4 проходят в GitHub Actions. Диагностический журнал
публикуется как `px4-sitl-read-only-synthetic-replay`.
Описание протокола и ограничений:
`docs/PX4_SITL_READONLY_REPLAY_RU.md`.


В PX4 shell, только диагностика:

```sh
ofnav start -r 100 -q 120
```

## Принятая система координат

В Python-демонстраторе используется упрощенная горизонтальная NED/ENU-совместимая плоскость:

- `n` — продольная горизонтальная координата, м;
- `e` — поперечная горизонтальная координата, м;
- `vx_body` — скорость вперед по оси X корпуса БВС, м/с;
- `vy_body` — скорость вправо по оси Y корпуса БВС, м/с;
- `yaw` — курс БВС, рад.

Для `MAVLink OPTICAL_FLOW_RAD` используется следующее приближение:

```text
flow_x_rate = (integrated_x - integrated_xgyro) / dt
flow_y_rate = (integrated_y - integrated_ygyro) / dt

vx_body =  height * flow_y_rate
vy_body = -height * flow_x_rate
```

В RTOS-ядре модель расширена:

```text
v_sensor_x =  height * flow_y_rate * flow_scale_y
v_sensor_y = -height * flow_x_rate * flow_scale_x
v_body_at_sensor = R_body_sensor * v_sensor
v_body_at_cg = v_body_at_sensor - omega_body × r_sensor_body
v_nav = R_yaw * v_body_at_cg
```

Знак по Y важен: линейное движение датчика по положительной оси Y дает отрицательный поток вокруг X.

## Состав синтетического лога

Основные поля:

- `t_s` — время, с;
- `true_n_m`, `true_e_m` — истинное относительное положение, м;
- `true_vn_mps`, `true_ve_mps` — истинная горизонтальная скорость, м/с;
- `true_alt_m` — истинная высота над подстилающей поверхностью, м;
- `roll_rad`, `pitch_rad`, `yaw_rad` — ориентация БВС;
- `gyro_x_radps`, `gyro_y_radps`, `gyro_z_radps` — гироскопы;
- `acc_x_mps2`, `acc_y_mps2` — горизонтальные ускорения в связанной СК;
- `range_m` — дальномер, м;
- `of_integrated_x_rad`, `of_integrated_y_rad` — интегральный оптический поток, рад;
- `of_integrated_xgyro_rad`, `of_integrated_ygyro_rad`, `of_integrated_zgyro_rad` — интегральные угловые скорости, рад;
- `of_quality` — качество ОП, 0...255;
- `texture_class` — тип поверхности;
- `light_lux` — освещенность;
- `gps_available` — признак доступности ГНСС.

В генераторе заложены реалистичные деградации:

- участок слабой текстуры;
- участок вибраций;
- кратковременная потеря дальномера;
- участок плохой освещенности/дыма.

## Связь с реальным автопилотом

Для PX4 штатный путь — чтобы датчик ОП публиковал `OPTICAL_FLOW_RAD`, а дальномер — `DISTANCE_SENSOR`; EKF2 использует ОП при наличии валидного дальномера, включенном контроле ОП и достаточном качестве. Для ArduPilot аналогично требуются корректные параметры датчика ОП, ориентации, дальномера и проверка логов.

`src/mavlink_bridge.py` — диагностический модуль. Он читает поток MAVLink, вычисляет скорость по ОП и может логировать результат. Передача оценок внешней скорости в автопилот через companion computer должна включаться только после проверки параметров EKF/External Vision на конкретной прошивке.

`firmware/rtos_core` — переносимое ядро для настоящей бортовой реализации.

`integrations/px4_ofnav_module` — PX4 uORB/NuttX-модуль, который запускает RTOS-ядро внутри настоящего PX4 flight stack и содержит заготовку интерфейса внешней одометрии; слияние заблокировано до проверки трехкомпонентной скорости.

## Рекомендуемые параметры для первого этапа

### PX4, общий ориентир

```text
EKF2_OF_CTRL      = включить штатное использование optical flow, если используется штатный ОП-канал PX4
EKF2_OF_QMIN      = 100...150 для первого этапа
SENS_FLOW_MINHGT  = 0.15...0.30 м
SENS_FLOW_MAXHGT  = 3.0...5.0 м для малых высот
EKF2_OF_POS_X/Y/Z = фактическое смещение датчика от центра масс
```

### PX4, fusion-output через `ofnav -e`

```text
EKF2_EV_CTRL      = 4     # только external vision velocity bit
EKF2_EV_NOISE_MD  = 0     # использовать параметры шумов EKF2
EKF2_EVV_NOISE    = 0.30  # начальное консервативное значение, уточняется по логам
```

### ArduPilot, общий ориентир

```text
FLOW_TYPE         = тип установленного датчика
FLOW_ORIENT_YAW   = ориентация датчика
FLOW_FXSCALER     = масштаб по X
FLOW_FYSCALER     = масштаб по Y
RNGFND1_TYPE      = тип дальномера
RNGFND1_MIN_CM    = минимальная дальность
RNGFND1_MAX_CM    = максимальная дальность
LOG_DISARMED      = 1 для стендовой проверки
```

Конкретные значения зависят от датчика, прошивки, ориентации установки и версии автопилота.

## Безопасность

Перед летными испытаниями:

1. снять винты на стендовой проверке;
2. проверить знаки `OF.flowX/flowY` относительно `IMU.GyrX/GyrY`;
3. проверить дальномер на фактической высоте;
4. ограничить углы крена/тангажа;
5. ограничить горизонтальную скорость;
6. сначала проверить `debug_vect`, затем `vehicle_visual_odometry`, и только потом включать fusion в EKF2;
7. выполнять первый полет только с внешним пилотом и возможностью ручного перехвата.

К реальному полету допускается не Python-скрипт, а прошитая и проверенная интеграция RTOS-ядра со штатным автопилотом и его failsafe-логикой.
