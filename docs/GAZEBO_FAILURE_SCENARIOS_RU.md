# Сценарии отказов в замкнутом контуре: PX4 SITL + Gazebo, армирование

## Что было

`SafetyActionManager` и отправка `vehicle_command` проверялись
модульными тестами и в неармированном SITL без симулятора. Цепочка
«отказ датчика → режим навигации → действие → commander PX4 →
поведение аппарата» в полете не проверялась.

## Что сделано

`tools/gz_failure_scenarios.py` — PX4 v1.16.2 SITL, Gazebo Harmonic,
`gz_x500_flow` (камера ОП 100×100 пикс., 42°, PX4 OpenCV-поток;
лидар вниз). Скрипт поднимает PX4 и Gazebo без графики, подключается
как наземная станция MAVLink (heartbeat, центрированный
`MANUAL_CONTROL` — пилот не трогает ручки), армирует, взлетает на
2 м, переводит в POSCTL и запускает `ofnav start -p flow -a -q 60`.

| № | Сценарий | Ожидается |
|---|---|---|
| 0 | на земле, не армирован | 0 команд |
| — | зависание POSCTL | `FLOW_NAV`, действие `NONE` |
| 1 | потеря ОП (`ofnav fault flow`) | `ALTITUDE_HOLD` → ALTCTL, высота сохранена; после восстановления `NONE`, аппарат **остается** в ALTCTL |
| 2 | подъем выше 4 м (диапазон датчика ОП) | `HEIGHT_TOO_HIGH` → `ALTITUDE_HOLD` → ALTCTL |
| 3 | потеря дальномера (`ofnav fault range`) | `FAILSAFE_LAND` → `LAND` (фиксируется) → AUTO.LAND, посадка, разоружение |
| 4 | второй полет: отказ ИИМ (`ofnav fault imu`) | менеджер сброшен новым армированием (действие `NONE`); `FAILSAFE_LAND` → `LAND` (фиксируется, причина `FAILSAFE_CONFIRMED`) → AUTO.LAND, посадка, разоружение |

Gazebo в PX4 не реализует `failure optical_flow/distance_sensor`,
поэтому отказ имитируется маскированием входа модуля
(`ofnav fault flow|range|none`, только сборки POSIX). Все ожидания и
паузы — во **времени симуляции** (`time_boot_ms` MAVLink): программная
отрисовка Gazebo дает коэффициент реального времени 0,1–1 в
зависимости от машины. Отчет — JSON, код возврата ≠ 0 при любом сбое.

### Сцена с текстурой

Стандартные миры дают камере ОП качество 0–60 из 255: однотонная
плоскость (`default`), редкие маркеры (`aruco`), тяжелый рельеф
с низкой частотой кадров (`baylands`). Скрипт создает мир
`ofnav_textured`: мир `default` с текстурой 20×20 м из случайных
пятен нескольких масштабов (1 см/пикс., детерминированное зерно).
Качество потока в полете — 150–185.

## Найдено и исправлено в замкнутом контуре

1. **Действие при взлете.** До взлета дальномер показывает < 0,2 м
   (ниже диапазона), деградация подтверждалась, и при отрыве
   выдавались `ALTITUDE_HOLD`, а через 5 с — `LAND`: взлет срывался.
   Исправлено: действия только в воздухе (`vehicle_land_detected`)
   и после установившейся навигации (`FLOW_NAV` 1 с в полете);
   сброс менеджера при армировании (`docs/SAFETY_ACTIONS_RU.md`).
2. **Нет гироскопа у датчика ОП.** В `gz_bridge` (и у PAW3902-класса)
   `delta_angle_available = false`; прежний модуль отбрасывал все
   отсчеты. Добавлен `ofnav::GyroIntegrator`: гироскоп аппарата
   (`vehicle_imu`, без прореживания) интегрируется ровно по интервалу
   потока с долевым учетом пакетов на краях; при неполном покрытии
   отсчет ждет следующий пакет ИИМ (не более 50 мс) и иначе
   отклоняется, а не компенсируется нулем.
3. **Блокировка шлюза обновления горизонтального фильтра.** На земле
   и при взлете ОП недоступен, скорость интегрируется по акселерометру
   и уходит на 4 м/с при оптимистичной ковариации; затем
   χ²-шлюз отвергает все верные измерения навсегда
   (`INNOVATION_GATE`). Исправлено как в EKF2: если с последнего
   принятого измерения прошло более `velocity_reset_timeout_us` (1 с),
   прошедшее остальные проверки измерение ОП **переинициализирует**
   скорость (`HorizontalEkf::resetVelocity`, счетчик `vel_resets`).
   Одиночный выброс при непрерывной коррекции по-прежнему
   отклоняется (тест `test_velocity_reset_after_aiding_outage_but_not_during_aiding`).
4. **Пустые отсчеты симулятора.** Библиотека потока PX4
   (`OpticalFlow::limitRate`) для кадра, который еще не выдается,
   возвращает качество −1 (255 в uORB). Такие отсчеты (устройство
   `DRV_FLOW_DEVTYPE_SIM`, качество 255) отбрасываются
   (`sim_placeholders` в status); раньше они давали «хорошее качество»
   в статистике.

   **Исправление (полет без ГНСС, `docs/GNSS_DENIED_SITL_FLIGHT_RU.md`).**
   Первая версия добавляла интервал отброшенного отсчета к следующему
   по предположению, что поток следующего отсчета покрывает оба
   интервала. Сравнение с эталоном Gazebo показало обратное: скорость
   ОП была 0,66–0,68 истинной. Поток выданного отсчета покрывает только
   его собственный интервал. Теперь отсчет-заглушка просто отбрасывается;
   отношение скорости `ofnav` к истинной — 1,00–1,02. Сценарии отказов
   этот множитель не выявляли: они проверяют режимы, а не точность
   скорости.

`ofnav status` дополнен гистограммой причин отклонения, последним
отсчетом потока (сырой поток, гироскоп, интервал, качество, высота,
скорость) и скоростью фильтра.

## Результат

Окончательный прогон (`ofnav_textured`, все ожидания во времени
симуляции):

| № | Проверка | Результат |
|---|---|---|
| 0 | не армирован, 0 команд | PASS, `NONE` |
| — | зависание POSCTL на 2 м | PASS, 278 отсчетов `FLOW_NAV`, `NONE`, качество 150–185 |
| 1 | потеря ОП 2,5 с | PASS: `ALTITUDE_HOLD` → ALTCTL, Δh = 0,0 м; восстановление до `NONE` за 1,0 с, аппарат остался в ALTCTL |
| 2 | подъем до 4,16 м | PASS: `HEIGHT_TOO_HIGH` → `ALTITUDE_HOLD` → ALTCTL |
| 3 | потеря дальномера | PASS: `LAND` (зафиксирован и после восстановления дальномера) → AUTO.LAND → посадка → разоружение; всего 3 команды |
| 4 | второй полет, отказ ИИМ | PASS: после нового армирования действие `NONE` (фиксация `LAND` первого полета сброшена); `LAND` по `FAILSAFE_CONFIRMED` → AUTO.LAND → посадка → разоружение |

Сценарии 3 и 4 сначала не проходили: PX4 прерывал AUTO.LAND
сообщением «Pilot took over using sticks». Стенд перед сценарием 3
двигает ручку газа (спуск после сценария 2), и commander счел это
перехватом управления пилотом. Это свойство стенда, а не `ofnav`:
параметры задаются при загрузке, в том числе `COM_RC_OVERRIDE=0`.
На реальном аппарате перехват пилотом должен оставаться включенным.

Промежуточный прогон с потерей ОП 3,5 с (ожидание ALTCTL + 3 с)
закончился `LAND` по `DEGRADED_TOO_LONG`: потеря плюс 1 с
восстановления превысили 5 с эскалации. Это проектное поведение,
поэтому сценарий 1 проверяет **кратковременную** потерю; при длительной
потере посадка — ожидаемая реакция.

## Воспроизведение

```sh
make -C PX4-Autopilot px4_sitl_default     # с модулем ofnav, gz Harmonic
pip install pymavlink numpy pillow
python tools/gz_failure_scenarios.py PX4-Autopilot --out build/gz
cat build/gz/gz_failure_scenarios.json
```

## Ограничения

- Отказы имитируются на входе модуля, а не в модели датчика Gazebo.
- Рассогласование ориентации и выход из диапазона наклона не проверялись.
- В `gz_x500_flow` нет ГНСС: в этих сценариях EKF2 PX4 держит
  положение по **собственному** слиянию оптического потока, а `ofnav`
  только отвечает за реакцию на отказы. Полет, в котором единственная
  горизонтальная коррекция EKF2 — `ofnav`, описан в
  `docs/GNSS_DENIED_SITL_FLIGHT_RU.md`.
- Порог качества `-q 60` подобран для камеры симулятора.
- Прогон занимает 10–40 мин в зависимости от скорости отрисовки и в
  CI не включен.
