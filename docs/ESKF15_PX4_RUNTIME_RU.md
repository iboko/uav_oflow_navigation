# 15-мерный РФК внутри PX4: стек, время, исполнение

## Что было

`ofnav15::FixedLag` компилировался в составе PX4, но не запускался.
Временные матрицы 15×15 размещались на стеке: статический анализ
(`-fstack-usage`) давал ≈11 КиБ для `predict`, ≈8 КиБ для коррекции,
по цепочке пересчета — около 20 КиБ, при стеке задачи 4 КиБ.
Время пересчета не измерялось.

## Что сделано

### 1. Стек

Все крупные временные данные перенесены в `ofnav15::Workspace`
(18,5 КиБ), который является членом `FixedLag` и выделяется
один раз вместе с объектом. Добавлены `Filter::reset()` и
`FixedLag::reset()` без временных объектов на стеке.
Произведение `exp(FΔt)` считается по схеме Горнера
(две рабочие матрицы вместо пяти).

Измерение — `firmware/rtos_core/tests/eskf15_benchmark.cpp`
(CTest `eskf15_resource_budget`): поток с заранее закрашенным
стеком, базовая линия пустого потока вычитается (glibc
размещает TCB/TLS внутри пользовательского стека).

| Сборка хоста | Стек цепочки фильтра |
|---|---|
| отладочная (CI) | 2,1 КиБ |
| Release | 1,9 КиБ |
| Release, `LD_BIND_NOW=1` | 0,25 КиБ |

Разница без `LD_BIND_NOW` — кадр ленивого связывания glibc.
Бюджет теста — 3 КиБ; стек задачи PX4 `ofnav` увеличен до 8 КиБ
(`kTaskStackBytes`): 3 КиБ на фильтр, остальное — цикл модуля,
uORB и журнал.

### 2. Время

Две оптимизации без изменения математики:

- все измерения одного кадра вставляются **одним** пересчетом
  (`pushDelayedFrame`);
- до 4 промежуточных снимков состояния через каждые 12 отсчетов ИИМ:
  пересчет начинается с ближайшего снимка старше измерения, а не
  с контрольной точки. Снимки, затронутые неудачным пересчетом,
  объявляются недействительными.

Эквивалентность последовательному фильтру проверяется тестом
`test_snapshot_replay_equals_sequential_filter` (до 1e-9) и
сравнением C++/Python по всем 225 элементам ковариации.

Бенчмарк: 64 отсчета ИИМ в истории, кадр из пяти видов
измерений каждые 0,1 с, задержка 60 мс.

| Величина (Release, x86-64) | Значение |
|---|---|
| `pushImu`, среднее | 0,03–0,05 мс |
| кадр, среднее / худшее | 0,2–0,3 / 0,4–0,9 мс |
| длина пересчета | ≤ 17 отсчетов ИИМ (было 64) |
| `sizeof(FixedLag)` | 48 КиБ |

Внутри исполняемого PX4 SITL (`ofnav sitl-eskf`, тот же поток ИИМ+VO
стенда): шаг ИИМ — 33 мкс в среднем (136 мкс худший), кадр — 1 мс
в среднем (3,4 мс худший, холодный старт).

**Оценка для полетного контроллера** (не измерение): прогноз ≈19 тыс.
умножений-сложений double, коррекция ≈10 тыс.; худший кадр ≈0,4 млн.
Для Cortex-M7 480 МГц с FPU двойной точности при 4–8 тактах на
операцию: 3,5–7 мс на кадр и 0,3–0,6 мс на шаг ИИМ, т.е. 7–13 %
ядра при 100 Гц ИИМ и 10 Гц камеры. Для Cortex-M4 (FPU только
одинарной точности) реализация на double непригодна.

### 3. Исполнение в PX4

`firmware/rtos_core/include/ofnav/eskf_runner.hpp` — независимый от
PX4 класс `EskfRunner` (тест `test_eskf_runner`):

- накопление пакетов `vehicle_imu` (Δθ, Δv) до 100 Гц; насыщение
  (clipping) сбрасывает частичный отсчет, разрыв > 50 мс
  перезапускает фильтр;
- инициализация: статическая выставка за 1 с (крен/тангаж по
  ускорению, смещение гироскопов), курс — от автопилота с СКО 0,1 рад;
  при движении/вибрации — запасная инициализация по `vehicle_attitude`;
- коррекция — скорость центра масс **в осях корпуса** из ядра ОП/VO
  с СКО профиля (`docs/SENSOR_PROFILES_RU.md`); измерение новее
  последнего отсчета ИИМ ждет его поступления;
- статистика времени (`hrt_absolute_time`), длины пересчета,
  отказов и перезапусков.

Модуль `ofnav` запускает раннер по умолчанию (`-d` отключает):

```sh
ofnav start -p camera
ofnav status        # eskf mode/init/status, тайминги, скорость, смещения
listener debug_vect # OFNAV_E: VN, VE, 100*mode+status; OFNAV_T: тайминги
```

**Оценка не публикуется в EKF2 и не используется в управлении**
(`-e` по-прежнему отвергается).

### 4. Проверка в CI

`tools/run_px4_sitl_replay_smoke.sh` в собранном PX4 v1.16.2:

1. `sitl-replay` с профилями `flow` и `camera`;
2. `ofnav start -p camera` + `status` — живой модуль с ESKF;
3. `ofnav sitl-eskf <events.csv>` — РФК внутри процесса PX4 на потоке
   ИИМ + запаздывающей VO, конечное состояние совпадает с эталоном
   Python (`--eskf-expected-json`) с допуском 1e-6.

Исправлено: smoke-скрипт завершал подоболочку, а не процесс PX4
(`exec`), из-за чего локально оставался сервер PX4.

## Ограничения

Время и стек измерены на x86-64 и в PX4 SITL. На полетном
контроллере (NuttX) они не измерены; в SITL с lockstep без
симулятора `hrt_absolute_time` не идет, поэтому `sitl-eskf`
использует системные часы.
