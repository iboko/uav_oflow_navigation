# Картографическая привязка БВС по ортофотоплану: офлайн-прототип

**Назначение:** ограниченно применимая независимая картографическая
локализация по изображению нижней камеры для оценки накопленного
дрейфа визуально-инерциальной одометрии без ГНСС.

**Состояние:** математический и программный прототип. Сопоставление
с ортофотопланом НЕ доказывает точность удержания БВС на высоте
100 м. Вычисленная позиция **не передается** в PX4 и не вносится
автоматически в 15-мерный РФК.

## 1. Математическая модель и обозначения

Приняты:
- **FRD:** связанная система координат БВС — вперед, вправо, вниз
- **NED:** навигационная система координат — север, восток, вниз
- **СК камеры:** X вправо изображения, Y вниз изображения,
  Z по оптической оси
- **ортофотоплан:** растровая местность с явной плановой
  привязкой пикселей к двум координатам N/E **в метрах**

Ортофотоплан требуется предварительно привести к единой
локальной метрической СК и общему датуму. Использование
широты/долготы в градусах в качестве координат N/E
недопустимо. Координаты центра пикселя ортофотоплана:

```text
[N,E]^T = [N0,E0]^T + A_ne_from_map_pixel [u_map,v_map]^T
```

Матрица A (2×2) допускает поворот сетки ортофотоплана;
ее столбцы представляют физические перемещения N/E
при сдвиге на один пиксель по горизонтали и вертикали.
Учитываются также отрицательные направления строк карты.

Для кадра с устраненной дисторсией выполняются
поиск и сопоставление характерных точек (ORB),
дескрипторная проверка относительного расстояния,
оценивание проективного преобразования **RANSAC** и
контроль числа, доли и пространственного распределения
геометрически согласованных соответствий. Если
`H` преобразует пиксель кадра в пиксель карты:

```text
p_map ≈ H(p_camera_pixel)
p_ground_N/E = map_affine(H(camera_principal_point))
```

Для получения координаты **центра масс БВС**,
а не участка земли под оптической осью, применяется
модель пересечения оптического луча с плоской
подстилающей поверхностью:

```text
ray_camera = [(u-cx)/fx, (v-cy)/fy, 1]^T
ray_NED = R_nb R_bc ray_camera
delta_ground_NE = height_agl * ray_NE / ray_D
p_vehicle_NE = p_ground_NE
              - delta_ground_NE
              - (R_nb * camera_offset_body)_NE
```

В `height_agl` задают расстояние **от оптического центра
камеры до локальной горизонтальной плоскости земли** по
вертикали. Если высотомер измеряет вдоль луча или от
другой точки БВС, значение необходимо привести
по схеме установки. Данные об уклоне и рельефе
здесь не восстанавливаются.

Найденное соответствие также сравнивается с
калиброванным пространственным масштабом изображения
`height/focal_length`, курсом и ориентацией
камеры через **полный локальный якобиан преобразования**.
Поэтому даже большое число визуальных соответствий
не является достаточным условием принятия.

## 2. Ограничения по неоднозначности

Модуль `src/orthophoto_localization.py` сравнивает
несколько указанных листов карты. Если сопоставимые
по числу согласованных точек альтернативы дают
несколько возможных привязок, возвращает
`AMBIGUOUS_MAP_MATCH`, не координату.

**Это не исчерпывает неоднозначность.** Повторяющиеся
дороги, крыши, сельскохозяйственные поля и однотипные
структуры даже внутри **одного** листа могут дать
ложное геометрически согласованное соответствие.
Без независимой оценки целостности решения и
повторной проверки на разных кадрах глобальную
привязку считать доказанной нельзя.

Отказы: `INSUFFICIENT_TEXTURE`,
`UNSUPPORTED_ATTITUDE`, `UNSUPPORTED_HEIGHT`,
`NO_GEOMETRICALLY_VALID_MAP_MATCH` и
`AMBIGUOUS_MAP_MATCH`. Ни один из этих статусов
не должен приводить к использованию последней
ошибочной коррекции положения.

## 3. Почему карта еще не корректирует РФК автоматически

Факт успешного RANSAC не определяет статистическую
ковариацию картографической координаты. Ошибки
возникают из калибровки объектива, геопривязки
ортофотоплана, высоты, синхронизации, рельефа,
подвижных объектов и освещения. Пиксельный
остаток RANSAC **нельзя** объявлять
среднеквадратической ошибкой координат БВС.

Второй принципиальный вопрос: картографическая
локализация и визуальная одометрия обычно используют
**те же кадры**. Следовательно, их ошибки могут
быть взаимно коррелированы. Простейшая инновационная
матрица `S = P + R` допустима только при
независимых погрешностях. Без проверки этого
предположения или учета перекрестной ковариации
внесение поправки в РФК некорректно.

Поэтому `src/map_correction_gate.py` создает
только **кандидат на коррекцию**. Для допуска
дополнительно требуются:
- внешняя экспериментально проверенная
  ковариация измерений карты
- подтверждение независимости погрешностей
  или **отдельно разработанный** алгоритм учета
  перекрестных ковариаций
- согласованные временные метки и местная СК
- статистическая проверка инновации и физическое
  ограничение на скачок координат

Даже если все проверки выполнены, выходной статус
`CANDIDATE_ONLY_NOT_APPLIED` **не означает**, что
изменения внесены в РФК. В этом PR механизм
применения отсутствует намеренно.

## 4. Исходные данные и воспроизводимая проверка

В `map_config.yaml` указывают:

```yaml
camera:
  focal_x_px: 1000
  focal_y_px: 1000
  center_x_px: 320
  center_y_px: 240
  image_to_body_xy: [[0, -1], [1, 0]]
  body_from_camera: [[0, -1, 0], [1, 0, 0], [0, 0, 1]]
  camera_offset_body_m: [0, 0, 0]
map_tiles:
  - name: orthophoto_01
    image_path: orthophoto.png
    origin_ne_m: [100, -50]
    matrix_ne_m_per_px: [[0, -0.1], [0.1, 0]]
# Заполняется ТОЛЬКО после независимой оценки точности карты:
# map_covariance_ne_m2: [[0.1, 0], [0, 0.1]]
# map_error_statistics_validated: true
# measurement_errors_independent_from_prior: true
```

Числа в примере **синтетические**, не являются
измеренными параметрами камеры НИИВК или точностью
ортофотоплана. Последние две настройки нельзя
включать без самостоятельной проверки корреляции.

В `camera_frames.csv` (каждый кадр заранее
исправлен по дисторсии) указывают:

```csv
timestamp_us,image_path,height_agl_m,roll_rad,pitch_rad,yaw_rad
1000000,frames/000001.png,100,0,0,0
1100000,frames/000002.png,100,0,0,0
```

Время относится к **середине экспозиции**.
Углы должны быть синхронизированы с кадром в
тех же системах координат. Для дополнительной
диагностики допускаются необязательные поля
`predicted_n_m,predicted_e_m,pred_cov_nn_m2,
pred_cov_ne_m2,pred_cov_ee_m2` (все пять вместе).

```bash
python -m pip install -e '.[dev,vision]'
python -m src.run_orthophoto_localization \
  --manifest data/camera_frames.csv \
  --configuration data/map_config.yaml \
  --output-dir outputs/map_localization
```

Результаты:
- `orthophoto_candidates.csv`: предложенные координаты N/E,
  имя листа, число совпадений, геометрический остаток,
  доля согласованных точек, статус проверки,
  отметка `applied_to_estimator=0`
- `orthophoto_summary.json`: доля геометрически
  приемлемых совпадений, причины отказов и пределы
  использования результата

## 5. Экспериментальный план НИИВК

Потребуются: геопривязанный ортофотоплан
с паспортом пространственной точности,
параметры камеры и ее установки, высота с
известной точкой отсчета, синхронизированная
ориентация, независимый эталон N/E и видеокадры.

Проверки разделить по высотам 20, 50 и 100 м,
погоде, освещению, наклонам камеры, текстуре,
повторяющимся структурам и отличиям между
датой съемки карты и датой испытания.
Отдельно проверить: долю **ложных принятых
привязок**, долю отказов на пригодных кадрах,
смещение, среднеквадратическую ошибку
координат и временную устойчивость на
независимых полетах.

Дальнейший этап — оценка статистической
неопределенности картографической привязки
на независимых логах, несколько кадров и
контроль целостности, затем осторожное
сопряжение с задержанным 15-мерным РФК.

**До этого запрещено утверждать, что
задача длительного зависания БВС без ГНСС
на высоте 100 м решена.**
